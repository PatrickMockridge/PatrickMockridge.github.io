Proof of computation

Mudra

Prove that a committed calculation trace is unchanged — and, when the witness is shared for replay, that it was executed correctly — without revealing the model.

What
A proof-of-trace system: it binds a program digest, input/output hashes, the return value, and the step count in a constant-size proof. It does not constrain each instruction; per-instruction correctness comes from deterministic replay with the witness, or from trusting the prover.
Why
A hash on Arweave proves a file existed. It does not prove the math inside it was right. Regulated work still moves as spreadsheets and sealed models, and the counterparty has to trust the vendor’s black box. Mudra replaces that trust with a receipt the other side can verify. What a regulator or counterparty needs is not “here is our file hash”, but “here is proof this calculation produced this number, and you can check it without seeing our model.” The case studies are insurance brokering and fiscal metering.
The combination
A BigInt-native ZK VM + a constant-size Halo2 hash-chain seal (~6 KB; one verifying key for every program) + an Arweave receipt with an entropy beacon.

Method

Specify the failure mode before the architecture; prove what can be proved; contain what cannot; record provenance with every result. Where proof stops is stated in the limits.

2Design

  • Prove the trace, not just the file. The proof binds a program digest, input and output hashes, the return value, the step count, and the specification digest into one seal; a file hash cannot. It does not constrain each instruction; replay does that.
  • Keep the formulas private. The proof contains fingerprints, not the spreadsheet; the program, inputs, and business logic stay on the prover’s machine. Encrypted witness sharing is optional for a counterparty that must replay.
  • Use one circuit for every program. The Halo2 circuit seals a Poseidon hash chain across 21 field elements; it is constant-size regardless of the program, so every program uses the same verifying key. Halo2 is the seal, not the execution engine.
  • Make the seed independently chosen. The entropy beacon derives the seed from Arweave block hashes that did not exist when the intent was posted, so a prover cannot rerun with favourable seeds and publish only the best result.
  • Verify anywhere. A lightweight WASM verifier checks the hash chain in a browser, on a phone, or from the CLI.

3Provenance

Mudra is extracted from DarkFi; the ZK VM lineage is inherited. The spreadsheet transpiler, the constant-circuit hash-chain seal, the verifier WASM, the Arweave receipt pipeline, the entropy beacon, and the Lean 4 specification are the project’s work. The code is AGPL-3.0-only.

5Limits

  • Research build; not a production audit system; no third-party audit is claimed.
  • The circuit seals a hash chain, not every instruction. Per-instruction correctness relies on deterministic replay; a verifier with only the proof and public inputs cannot check it without the witness. The encrypted-witness path is how that can be shared without publishing the model. If you need per-opcode constraints, use RISC Zero, SP1, or zkWASM.
  • Proving runs on a single machine and needs the ~2 MB Halo2 parameters for k=15; distributed proving is future work.
  • The entropy beacon adds roughly six minutes of latency and requires Arweave gateways; the instant path uses a user-supplied seed.
  • The spreadsheet transpiler supports a subset of spreadsheet functions — 33 in the insurance case study — and roughly 1,024 dense cells; it is not a full Excel engine.
  • The browser-side verifier is a lightweight check; full Halo2 verification uses the CLI with the parameters.
